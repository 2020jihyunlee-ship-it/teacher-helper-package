1. 진단 — 지금 무엇이 없어서 수동인가

부서 패키지 설치는 3개 층으로 이뤄진다. 실측 결과 2개는 이미 완성돼 있고, 1개만 없다.

층역할현재 상태
L1 선언무엇을 만들 것인가 (부서·기술자·경로)✅ manifest.json — 잘 만들어져 있음
L2 수렴선언과 실제 상태의 차이를 메움✅ tools/setup.ps1 503줄 — 견고함
L3 트리거누가 언제 L2를 실행시키는가❌ 없음 — 사람이 손으로 실행
연구의 정답은 L1·L2를 새로 만드는 게 아니라 L3를 얹는 것이다. 현재 setup.ps1은 이미 멱등·드라이런·원자저장·실패누적·검증보고를 갖춘 수준급 수렴기다. 버리면 손해다.
setup.ps1은 이미 범용 엔진이다 — 칼빈 전용 하드코딩이 사실상 없다. manifest.json을 읽어 그대로 수렴할 뿐이다. → 이름만 cys-pkg로 승격하면 어떤 부서 패키지든 설치할 수 있다. 교회패키지는 그 첫 적용 사례가 된다.

2. 이 PC 실측 결과

2-1. 칼빈 부서는 이미 설치돼 있다 (수동 1회 세팅분)

deptmission_keyparentcwd

dept-7fm-adminFuture Ministry(칼빈)...\행정관리부

parent 백필까지 정상. setup.ps1이 설계대로 동작했다는 실물 증거다.
⚠ 등록부-실물 괴리 — 레지스트리는 작업 폴더를 가리키는데 그 폴더가 지금 없다. 부서 등록은 살아 있으나 기술자 작업 폴더(클론된 리포 11개)는 사라진 상태다. [미확인] 소멸 경위.
→ 표준화가 반드시 다뤄야 할 실패 모드. 설치 = 1회 이벤트가 아니라 상시 수렴이어야 한다.

2-2. cys에는 «패키지 설치» 표면이 없다 (상류 확인 완료)

  • cys --help 전수 확인 — dept 계열 명령 없음. init-pack/pack-update는 팩 전용이지 부서 패키지용이 아니다.
  • 상류 idoforgod/cys-terminal 파일 702개 전수 조회 — install/setup/package 관련은 cys 본체 설치 문서뿐.
  • 부서 생성 실체는 팩 안의 bash 스크립트 ~/.cys/pack/bin/cys-dept(1101줄)이며 create <catalog-key> 서브커맨드가 실재한다.
표준은 우리가 만들어야 한다. 상류에 기대할 수 없다.

3. 표준이 반드시 지켜야 할 제약 9개 (전부 코드 실측)

이걸 어기면 자동화는 조용히 실패한다.

★ 지금 당장 걸리는 제약: C3
이 PC는 등록 7개 / 상한 8개 → 여유 1개. 칼빈은 부서 4개를 요구한다. 다만 create에는 REUSE_UP/REUSE_BOOTING/REUSE_DEAD 재사용 분기가 있어 같은 mission_key면 재사용된다(상한 면제).
→ 표준 설치기는 설치 전에 상한 여유를 먼저 계산해 알려야 한다. 현행 setup.ps1에 이 사전 점검이 없다 — 개선 포인트.
★ C2는 우리에게 열려 있다 — 이 세션 실측 CYS_ROLE은 unset이다. ACL은 env 기준이므로 설치 실행은 통과한다. 다만 이건 방어의 구멍이기도 하다 — [추정] 상류가 이 판정을 데몬 조회로 바꾸면 설치기가 막힐 수 있다. 표준은 CYS_ROLE을 명시적으로 비우고 실행하는 것을 계약에 넣어야 한다.

4. 「동일하게 세팅」의 합격 기준

저장소의 docs/design-preview.svg가 기준 화면이다. 거기서 뽑은 완료 조건 4개:

  1. 사이드바 DEPARTMENTS 트리에 Future Ministry(칼빈) 루트 + 하위 3부가 들여쓰기되어 표시
  2. 각 부 아래 기술자 pane 행 — 행정 3 · 예배교육 3 · 설교기획 5 = 총 11
  3. 각 부서 데몬에서 cys list 시 role=master 1좌석 + role=- 기술자 N좌석
  4. 각 기술자 좌석의 cwd에 리포가 실제 클론되어 있을 것
자동 설치기의 검증 단계는 이 4개를 증거로 출력해야 한다 — "설치했다"는 말이 아니라.

5. 권고 표준 — 3층 구조

L1 선언   package.json (매니페스트 규격 v2)   ← 패키지 제작자가 쓴다
L2 수렴   cys-pkg      (setup.ps1 일반화)     ← 우리가 만든다 · 멱등
L3 트리거 ①원커맨드 ②드롭폴더 ③스케줄러      ← 이번 연구의 핵심

L3-① 원커맨드 (A안 · 1순위)

사용자가 하는 일 = 한 줄 붙여넣기.

irm https://raw.githubusercontent.com/<org>/<repo>/main/install.ps1 | iex

이 한 줄이 내부에서: 전제 점검 → git clone → setup.ps1 -Apply → 검증 출력.

⚠ 보안 — irm|iex는 원격 코드를 무검증 실행한다. 표준에 넣으려면 최소한 ①고정 태그·커밋 핀 ②SHA256 대조 ③실행 전 요약 표시+확인 중 하나는 있어야 한다. (자비스 팩이 .minisig 서명을 쓰는 것과 같은 사상)

L3-② 드롭 폴더 (B안 · 2순위 — 요구에 가장 근접)

~/.cys/packages/
   └ future-ministry-dept/    ← 여기에 폴더를 넣기만 하면
        package.json          ← 자비스가 발견해서
        ...                   ← 알아서 설치

발화 지점 후보(실측으로 존재 확인)

  • 세션 시작 훅 — hooks/session-start.sh 체계가 이미 있다
  • 스케줄러 — cys schedule add로 주기 발화 가능 (데몬이 hot-reload)
동작: 미설치 패키지 발견 → 드라이런 요약을 먼저 제시 → 승인 시 수렴. 무단 자동 설치는 하지 않는다 — 부서 생성은 프로세스를 늘리는 비가역 조치다.

L3-③ 스케줄러 상시 수렴 (등록부-실물 괴리의 해법)

cys schedule add  →  하루 1회  cys-pkg verify

선언 대비 실제(부서·좌석·폴더)를 대조해 드리프트만 보고. 자동 복구는 승인제. → C6(기술자 전멸)과 2-1의 폴더 소실을 조기 발견하는 장치.
