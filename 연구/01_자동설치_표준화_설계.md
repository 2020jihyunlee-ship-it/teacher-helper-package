> 이 문서의 모든 사실은 **실측**이다. 추정은 [추정], 미확인은 [미확인]으로 표기했다.

## 0. 결정이 필요한 것 (맨 앞)

**Q. 자동화 트리거를 무엇으로 할 것인가 — 3안 중 택1(또는 조합).**

| 안 | 사용자가 하는 일 | 난이도 | 권고 |
|---|---|---|---|
| **A. 원커맨드** | PowerShell에 **한 줄** 붙여넣기 | 낮음(1~2일) | ★1순위 |
| **B. 드롭 폴더** | `~/.cys/packages/` 에 **폴더만 넣기** → 자비스가 알아서 | 중간(3~5일) | ★2순위(A 위에 얹음) |
| **C. GUI 버튼** | 자비스 앱에서 **클릭** | 높음(상류 기여 필요) | 장기 |

샤론 권고: **A로 시작해 B로 상시화**. A는 오늘의 `setup.ps1`을 거의 그대로 쓰고 포장만 바꾸면 되고,
B는 "가져오면 알아서 세팅"이라는 회장님 요구에 정확히 대응한다. C는 상류(idoforgod) 저장소를
건드려야 해서 우리 통제 밖이다.

## 1. 진단 — 지금 무엇이 없어서 수동인가

부서 패키지 설치는 **3개 층**으로 이뤄진다. 실측 결과 **2개는 이미 완성돼 있고, 1개만 없다.**

| 층 | 역할 | 현재 상태 |
|---|---|---|
| **L1 선언** | 무엇을 만들 것인가 (부서·기술자·경로) | ✅ `manifest.json` — 잘 만들어져 있음 |
| **L2 수렴** | 선언과 실제 상태의 차이를 메움 | ✅ `tools/setup.ps1` 503줄 — 견고함 |
| **L3 트리거** | **누가 언제 L2를 실행시키는가** | ❌ **없음 — 사람이 손으로 실행** |

★ **연구의 정답은 L1·L2를 새로 만드는 게 아니라 L3를 얹는 것이다.**
지금 `setup.ps1`은 이미 멱등·드라이런·원자저장·실패누적·검증보고를 갖춘 수준급 수렴기다.
버리면 손해다.

### 1-1. `setup.ps1`은 이미 «범용 엔진»이다 (중요)

칼빈 전용 하드코딩이 사실상 없다. 스크립트는 `manifest.json`을 읽어 그대로 수렴할 뿐이다.
→ **파일명만 바꿔 `cys-pkg` 로 승격하면 어떤 부서 패키지든 설치할 수 있다.**
   교회패키지는 그 첫 번째 적용 사례가 된다.

### 2-1. 칼빈 부서는 **이미 설치돼 있다** (회장님 수동 1회 세팅분)

`~/.cys/depts.json` 실측 — 부서 등록 7개, 그중 칼빈 계열 4개:

| dept | mission_key | parent | cwd |
|---|---|---|---|
| dept-2 | future-ministry | (루트) | `C:\lab\Future-Ministry` |
| dept-7 | fm-admin | Future Ministry(칼빈) | `...\행정관리부` |
| dept-8 | fm-worship | Future Ministry(칼빈) | `...\예배교육부` |
| dept-10 | fm-sermon | Future Ministry(칼빈) | `...\설교기획부` |

parent 백필까지 정상. `setup.ps1`이 설계대로 동작했다는 실물 증거다.

### 2-2. ⚠ 그런데 «등록부-실물 괴리»가 있다

`depts.json`은 `C:\lab\Future-Ministry`를 가리키는데 **그 폴더가 지금 없다**.
즉 부서 등록은 살아 있으나 기술자 작업 폴더(클론된 리포 11개)는 사라진 상태다.
[미확인] 폴더 삭제·이동 경위 — 회장님 확인 필요.

→ 표준화가 반드시 다뤄야 할 실패 모드. **설치 = 1회 이벤트가 아니라 상시 수렴이어야 한다.**

### 2-3. cys에는 «패키지 설치» 표면이 없다 (상류 확인 완료)

- `cys --help` 전수 확인 — `dept` 계열 명령 **없음**. `init-pack`/`pack-update`는 **팩** 전용이지 부서 패키지용이 아니다.
- 상류 `idoforgod/cys-terminal` 파일 702개 전수 조회 — `install`/`setup`/`package` 관련은 **cys 본체 설치 문서뿐**.
- 부서 생성 실체는 팩 안의 bash 스크립트 **`~/.cys/pack/bin/cys-dept`** (1101줄)이며, `create <catalog-key>` 서브커맨드가 실재한다.

→ **표준은 우리가 만들어야 한다.** 상류에 기대할 수 없다.

## 3. 표준이 반드시 지켜야 할 제약 9개 (전부 코드 실측)

이걸 어기면 자동화는 조용히 실패한다.

| # | 제약 | 근거(실측) | 위반 시 |
|---|---|---|---|
| **C1** | **카탈로그 선행** — `dept-catalog.json`에 키가 먼저 있어야 create 가능 | `cys-dept:735` | exit 4 |
| **C2** | **ACL** — `CYS_ROLE`이 set이고 `cso`가 아니면 부서 생성 차단 | `cys-dept:570-580` | **exit 7** |
| **C3** | **부서 수 상한** — live 부서 ≥ `CYS_DEPT_CAP`(기본 **8**) | `cys-dept:801-805` | **exit 8** |
| **C4** | **parent 백필** — create는 parent를 쓰지 않음. UI 트리 진실원은 `depts.json` | `setup.ps1` ⑤b 주석 | 하위 부가 루트로 평면화 |
| **C5** | **slug 계약** `^[a-z0-9_-]{1,32}$` | 상류 `DESIGN-dept-qualified-keys-v2.md` §3 | 키 정규화·충돌 |
| **C6** | **기술자는 phoenix 보호 밖** — role 없는 좌석이라 로스터에 담기지 않음 | `setup.ps1` 헤더 | **데몬 1회 재기동에 전멸** |
| **C7** | **BOM 금지** — cys-dept의 python `json.load`가 깨짐 | `setup.ps1` `Save-JsonAtomic` 주석 | 카탈로그 파손 |
| **C8** | **`close-surface --reap` 필수** — 기본값은 묘비를 심음 | `setup.ps1` ⑧ 주석 | **부서 폐역** |
| **C9** | **좌석 제거 시 데몬 동반 사망 위험** — 부서 cysd가 좌석의 자손일 수 있음 | `setup.ps1` `-RemoveMaster` 경고 | 데몬 사망 |

### ★ 지금 당장 걸리는 제약: C3 (부서 수 상한)

이 PC는 **등록 7개 / 상한 8개** → **여유 1개**.
칼빈은 부서 **4개**를 요구하므로, 만약 기존 4개가 죽은 상태에서 신규 생성으로 잡히면 **exit 8로 실패**한다.
다만 create에는 `REUSE_UP`/`REUSE_BOOTING`/`REUSE_DEAD` 재사용 분기가 있어 **같은 `mission_key`면 재사용**된다(cap 면제).
→ **표준 설치기는 설치 전에 cap 여유를 먼저 계산해 사용자에게 알려야 한다.** (현행 `setup.ps1`에 이 사전 점검이 없다 — 개선 포인트)

### ★ C2는 우리에게 유리하게 열려 있다

이 세션 실측: `CYS_ROLE`은 **unset**(내가 `claim-role master`로 등록해도 env는 비어 있음).
ACL은 env 기준이므로 **설치 실행은 통과한다.** 단 이건 방어의 구멍이기도 하다 —
[추정] 상류가 이 판정을 데몬 조회로 바꾸면 우리 설치기가 막힐 수 있다. 표준은 `CYS_ROLE`을
명시적으로 비우고 실행하는 것을 계약에 넣어야 한다.

## 4. 「동일하게 세팅」의 합격 기준 (기준 화면에서 도출)

저장소의 `docs/design-preview.svg`가 기준 화면이다. 거기서 뽑은 **완료 조건 4개**:

1. 사이드바 **DEPARTMENTS** 트리에 `Future Ministry(칼빈)` 루트 + 하위 3부가 **들여쓰기**되어 표시
2. 각 부 아래 **기술자 pane 행** — 행정 3 · 예배교육 3 · 설교기획 5 = **총 11**
3. 각 부서 데몬에서 `cys list` 시 **`role=master` 1좌석 + `role=-` 기술자 N좌석**
4. 각 기술자 좌석의 `cwd`에 **리포가 실제 클론**되어 있을 것

→ 자동 설치기의 검증 단계는 이 4개를 **증거로** 출력해야 한다("설치했다"는 말이 아니라).

## 5. 권고 표준 — 3층 구조

```
L1 선언   package.json (매니페스트 규격 v2)   ← 패키지 제작자가 쓴다
L2 수렴   cys-pkg      (setup.ps1 일반화)     ← 우리가 만든다 · 멱등
L3 트리거 ①원커맨드 ②드롭폴더 ③스케줄러      ← 이번 연구의 핵심
```

### L3-① 원커맨드 (A안 · 1순위)

사용자가 하는 일 = **한 줄 붙여넣기**.

```powershell
irm https://raw.githubusercontent.com/yijae78/future-ministry-dept/main/install.ps1 | iex
```

이 한 줄이 내부에서: 전제 점검 → `git clone` → `setup.ps1 -Apply` → 검증 출력.

- 장점: 오늘 자산 그대로. 하루 이틀이면 된다.
- ⚠ 보안: `irm|iex`는 **원격 코드를 무검증 실행**한다. 표준에 넣으려면 최소한
  ①고정 태그·커밋 핀 ②SHA256 대조 ③실행 전 요약 표시+확인 중 하나는 있어야 한다.
  (자비스 팩이 `.minisig` 서명을 쓰는 것과 같은 사상)

### L3-② 드롭 폴더 (B안 · 2순위 — 회장님 요구에 가장 근접)

```
~/.cys/packages/
   └ future-ministry-dept/    ← 여기에 폴더를 넣기만 하면
        package.json          ← 자비스가 발견해서
        ...                   ← 알아서 설치
```

발화 지점 후보(실측으로 존재 확인됨):
- **세션 시작 훅** — `~/.cys/pack-dept-*/hooks/session-start.sh` 체계가 이미 있다
- **스케줄러** — `cys schedule add` 로 주기 발화 가능 (데몬이 hot-reload)

동작: 미설치 패키지 발견 → **드라이런 요약을 회장님께 제시** → 승인 시 수렴.
(무단 자동 설치는 하지 않는다 — 부서 생성은 프로세스를 늘리는 비가역 조치)

### L3-③ 스케줄러 상시 수렴 (C9 «등록부-실물 괴리»의 해법)

```
cys schedule add  →  하루 1회 cys-pkg verify
```
선언 대비 실제(부서·좌석·폴더)를 대조해 **드리프트만 보고**. 자동 복구는 승인제.
→ C6(기술자 전멸)과 2-2(폴더 소실)를 조기 발견하는 장치.
