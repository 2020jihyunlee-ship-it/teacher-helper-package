# 1군 · 누구나 겪는 공통 문제

> 판정 기준: **이 PC의 이력과 무관하게, Windows에 cys를 새로 설치한 사용자에게도 동일하게
> 발생**하는가. 코드·플랫폼 분기에서 비롯된 것만 여기에 넣었다.

## W1. `cys doctor`가 검사하지 않은 항목을 `[OK]`로 집계한다 ★P1

**증상**
```
[OK  ] socket         소켓 진단은 unix 전용(skip)
[OK  ] startup-lock   락 진단은 unix 전용(skip)
요약: 7 OK · 2 WARN · 0 FAIL
```

**핵심** — 검사하지 **않은** 2건이 `[OK]`로 표시되고 요약 `7 OK`에 합산된다.
Windows 사용자는 실제보다 건강한 진단 결과를 받는다.

**왜 공통인가** — 플랫폼 분기 코드다. Windows면 무조건 이렇게 나온다.

**영향** — Windows의 소켓은 named pipe이고, 앱 재시작·데몬 재기동 문제가 집중되는 계층이다.
그 계층이 진단에서 빠졌는데, 빠졌다는 사실이 `[OK]`에 가려진다.
**사용자가 문제를 겪는 바로 그 순간 `doctor`는 "이상 없음"을 보고한다.**

**제안** — skip은 `[SKIP]`/`[N/A]`로 표기하고 요약 카운트에서 분리. 가능하면 named pipe 진단 추가.

**재현** — Windows에서 `cys doctor` 1회 실행.

---

## W2. role 없는 pane 좌석은 재기동 후 복원되지 않는다 ★P1

**사실** — 데몬 재기동 복원은 `desired_roster.json` 기준이고, 이 로스터는 **role을 키로 하는 맵**이다.
따라서 role 미등록 좌석은 담길 자리가 구조적으로 없다.

**영향** — **데몬이 한 번만 재기동해도 그 좌석들이 전부 사라진다.**
부서 패키지로 편성한 작업 좌석이 앱 재시작만으로 초기화된다.

**왜 공통인가** — 플랫폼 무관한 설계 사실이다. 다만 **Windows에서 체감이 크다** — 앱 재시작이
잦다는 사용자 관측이 있다(U1 참조). 재시작 빈도가 높을수록 노출이 잦다. [추정]

**제안** — 로스터 키를 (role, title) 복합키로 확장하거나, role 없는 좌석용 별도 복원 목록.

**참고** — 이 사실은 상류 배포 스크립트 헤더 주석에도 명시되어 있다. 알려진 설계 한계다.

## W3. PowerShell 5.1이 붙이는 BOM으로 팩 JSON이 파손된다 P2  ✔2차 재현 확증

**증상** — PS 5.1의 `Set-Content -Encoding UTF8`은 **BOM을 붙인다.**
팩의 python 측 `json.load`가 이를 읽지 못해 설정 파일이 깨진다.

**왜 공통인가** — PS 5.1은 Windows 기본 탑재 셸이다. PS 7을 따로 깔지 않은 사용자가 다수다. [추정]

**영향 범위** — PowerShell로 팩 JSON(카탈로그·레지스트리)을 쓰는 **모든 경로**.
Windows 안내 문서가 `Set-Content`를 예시로 들면 그대로 재발한다.

**현재 우회** — 배포 스크립트는 `Set-Content`를 피하고 .NET `UTF8Encoding($false)`로 직접 쓴 뒤
임시파일+원자 교체를 한다. 즉 **개별 스크립트가 각자 방어하고 있다.**

**제안** — python 로더에서 `utf-8-sig` 허용(1줄). 근본 해결이자 비용이 가장 낮다.

**2차 검증(2026-08-25·별도 세션)** — PS 5.1.26100.8655에서 독립 재현: 첫 바이트 `efbbbf` 확인,
`json.load(utf-8)` = JSONDecodeError, `utf-8-sig` = 성공. **증상·해법 모두 확증.**

---

## W4. 백신 락으로 cys 연속 호출이 실패한다 P2

**증상** — cys 프로세스를 짧은 간격으로 연속 호출하면 실패한다.

**왜 공통인가** — Defender는 Windows 기본 활성이다. 예외 등록을 한 사용자만 비껴간다.

**현재 우회** — 배포 스크립트가 호출 사이에 **1200ms 고정 지연**을 넣는다.

**영향** — 부서 4개 + 좌석 11개 편성이 지연만으로 15초 이상 늘어난다.

**제안** — 재시도+백오프로 대체. 또는 락 실패를 구분 가능한 종료코드로 노출해
호출자가 판단할 수 있게 한다.

---

## W5. PowerShell 5.1에서 native 명령 stderr가 예외로 승격된다 P3  ✔2차 재현 확증

**증상** — `$ErrorActionPreference='Stop'` + `2>&1` 조합에서 native 명령의 stderr **첫 줄**이
`NativeCommandError`(catch에 잡히는 실제 예외 타입: `RemoteException` — 2차 검증 실측)로 터진다. cys는 정상 진행 정보도 stderr로 내보내므로,
**정상 동작이 스크립트 중단으로 이어진다.**

**왜 공통인가** — PS 5.1 기본 동작이다.

**영향** — 일반 사용자는 겪지 않는다. cys를 스크립트로 감싸는 사람만 해당한다.

**제안** — Windows 스크립팅 문서에 이 함정 명시. [추정] 또는 정보성 출력을 stdout으로 분리.

## W6. PS 5.1이 BOM «없는» UTF-8 스크립트의 한글을 ANSI로 오독한다 P2  (2차 검증 발견)

**증상** — 한글 문자열·주석이 든 `.ps1`을 UTF-8(무BOM)로 저장해 실행하면
문자열이 CP949로 오독·파손되며 **파서 에러로 스크립트 전체가 실행 불능**이 된다. (2026-08-25 실측)

**핵심** — **W3과 정확히 반대 방향의 함정이다: JSON은 BOM이 있으면 깨지고, ps1은 BOM이 없으면 깨진다.**

**왜 공통인가** — PS 5.1 기본 동작. PS 7에서는 미발생(기본 UTF-8 해석) [실측].

**영향 범위** — 한글 안내문·주석이 든 배포 스크립트(setup.ps1 계열) 전부.

**제안** — 표준에 **파일 종류별 인코딩 계약** 명시: `JSON = UTF-8 무BOM` · `.ps1 = UTF-8 BOM(또는 ASCII)`.
자동설치 표준(01 문서)의 제약 목록에 **C10**으로 추가 검토.

# 2군 · 이 PC 고유 상태 (공통 아님 · 개발자 보고 대상 아님)

> 아래는 **이 PC의 사용 이력·설정** 때문에 생긴 것이다. 새 PC에 새로 설치하는 사용자는
> 겪지 않는다. 공통 문제와 섞으면 보고의 신뢰가 떨어지므로 분리했다.

## L1. 등록부에 있는 작업 폴더가 실물로 없다

- **실측** — 부서 레지스트리에 등록된 작업 디렉터리가 실제로 존재하지 않는다.
  등록은 살아 있고, 어떤 명령도 이 불일치를 보고하지 않는다.
- **원인** — 이 PC에서 과거 수동 설치 후 폴더가 삭제·이동된 것으로 보인다. [미확인] 경위
- **왜 로컬인가** — 새 설치에서는 발생하지 않는다.
- **다만 일반화 가치는 있다** — "레지스트리 cwd 실재 검사"가 `doctor`에 없다는 점은
  **W1과 같은 계층의 공백**이다. 제출한다면 W1에 묶어 «진단 공백» 한 건으로 다루는 편이 낫다.

## L2. 부서 등록 7개 / 상한 8개 — 여유 1

- **실측** — 부서 등록 7건. 기본 상한 `CYS_DEPT_CAP=8`.
- **영향** — 부서 4개를 요구하는 패키지를 신규 설치하면 상한에 걸린다.
  (같은 mission_key면 재사용되어 상한 면제 분기가 있다 — 코드 확인)
- **왜 로컬인가** — 부서를 여러 번 만든 이 PC의 이력이다. 신규 사용자는 여유 8개다.
- **다만 제품 관점 지적 1건** — 상한 초과는 설치 **도중** 종료코드로만 드러난다.
  설치 **전** 여유를 알려주는 사전 점검이 없다. 이건 공통 사항이나 결함은 아니고 개선 제안이다.

## L3. 사용자명이 한글인 경로 — 현재 정상 · 잠재 위험

- **실측** — 이 PC의 사용자 경로에 한글이 포함된다.
  동봉 python 런타임(3.12.10)은 **정상 동작**했다. bash↔python 왕복도 정상.
- **왜 로컬인가** — 사용자명은 사람마다 다르다.
- **다만 공통으로 넘어가는 부분이 있다** — 부서 패키지 매니페스트가 작업 폴더로
  **한글 폴더명 3개**(`행정관리부`·`예배교육부`·`설교기획부`)를 지정한다.
  즉 **사용자명이 영문이어도 한글 경로는 생긴다.**
  PowerShell↔bash↔python 3중 경유에서 인코딩 문제 가능성 [미검증].
- **인접 도구의 실패 실측(2차 검증 보강)** — cys는 아니나 같은 환경에서:
  ①Ollama가 한글 사용자명 경로에서 모델 로딩 실패(경로 이전+env로 해결) ②python http.server가
  한글 파일명 URL을 percent-encoding 없이는 404 처리 ③python 전반에 `PYTHONUTF8=1` 필요 사례.
  → 현재 cys 실패 증거 없음. **결함으로 보고하지 않는다.** 다만 «잠재»가 아니라
  **«인접 도구 실패 실측 있음»** 수준의 추적 항목이다.

# 3군 · 이미 해결된 문제 (개발자에게는 확인 정보)

> 커뮤니티 문서(SOWER, 2026-07-15)가 제기한 Windows 전용 결함 2건.
> **우리 환경 0.14.7에서 코드 실측 결과 둘 다 해결되어 있다.**

## F1. preflight `C53` self-test가 Windows에서만 FAIL — ✅ 해결됨

- **과거 원인** — `os.path.basename(argv[0])`을 `"cys"`와 정확 비교. Windows는 `cys.EXE`가
  반환되어 불일치 → verb 추출 실패 → Windows에서만 FAIL.
- **0.14.7 실측** — `.lower()`로 소문자화하고 `splitext`로 `.exe/.cmd/.bat/.ps1/.com`을
  제거한 뒤 비교한다. **커뮤니티 우회책과 같은 형태로 수정 완료.**

## F2. safe_path 하에서 형제 모듈 import 붕괴 — ✅ 해결됨

- **과거 원인** — 동봉 런타임이 safe_path로 기동되면 스크립트 폴더가 `sys.path`에서 빠져
  형제 모듈 import가 실패. 일부는 **fail-open(조용한 무력화)**으로 나타나 더 위험했다.
- **0.14.7 실측** — 형제 import 앞에 경로 가드가 추가되어 있다.
  주석에 **"2026-07-29 Windows 0.14.4 실측"** 근거와, `insert(0)`이 아닌 `append`를 택한
  이유(이름충돌 shadowing 차단)까지 기재되어 있다. **수정 완료.**

**→ 조치 제안** — 커뮤니티 문서는 이 2건을 아직 «upstream 미반영»으로 적고 있다.
   해결 사실을 알려 문서를 최신화할 가치가 있다. (fail-open 항목이라 더욱)

- **다만 W2와의 연결 가능성** — 재시작 후 «무언가 사라진다»는 증상이라면 W2가 원인일 수 있다.
  스크롤은 별개(UI 계층)로 보인다. [추정]

## W1이 P1인 이유

W1 자체의 손실은 작다. 그러나 **진단 계층에 있어 효과가 다른 문제에 곱해진다.**
사용자가 문제를 겪는 순간 `doctor`는 "7 OK"라고 답한다 — 검사하지 않은 2건을 OK로 세면서.
**다른 모든 문제의 발견을 지연시킨다.** 수정비용은 표기와 카운트 분리로 거의 0이다.

## 관점이 바뀌면 순서도 바뀐다 — 패키지 배포자 기준

| 순위 | ID | 이유 |
|---|---|---|
| 1 | **W2** | 설치를 성공시켜도 **재시작 한 번에 편성이 사라진다** — 자동 설치 표준화의 근본 위협 |
| 2 | **W3** | 카탈로그가 파손되면 **부서 선언 자체가 소실**된다 |
| 3 | **W4** | 설치 시간 증가 + 느린 PC에서 설치 실패 가능 |
| 4 | **W1** | 설치가 제대로 됐는지 확인할 도구의 신뢰도 문제 |

→ 개발자에게는 W1이, 배포자에게는 W2가 1순위다. **제출 시 이 차이를 명시하는 편이 낫다.**
